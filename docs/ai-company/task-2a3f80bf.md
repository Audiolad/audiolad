приоритет published, права, спорные связи, истечение, анализ/история, уже
освобождён, свободен. Исходные брони и продукты включены в каждую строку JSON,
поэтому смешанные случаи доступны для ручного рассмотрения. `used` без продукта
также защищён. Никакие frequency, query_text, analysis_status не переписываются.
Неанализированные 99 резервных тем нельзя автоматически объявить одобренными.

## Запуск без production

Нужны Node.js, `psql` и полная локальная копия БД с ролью PostgreSQL с BYPASSRLS или superuser. Частичное чтение через RLS
запрещено, чтобы не ошибиться в отсутствии брони. Нельзя использовать туннель на production под видом localhost.
URL и секреты задаются в окружении оператора, их нельзя сохранять в отчёт.
Скрипт отклоняет удалённые хосты и параметры переопределения подключения.

Без подключения и без изменений:

```sh
node scripts/audio-sprint-general-release.mjs > /tmp/osen-audit.sql
```

При уже заданном `AUDIO_SPRINT_DATABASE_URL` локальной копии:

```sh
node scripts/audio-sprint-general-release.mjs --execute > /tmp/osen-before.json
```

Аудит работает и до новой миграции. Сначала проверить строки и числа, сравнить
с ожидаемыми 199 темами и зафиксировать расхождения. Нулевой результат означает
отсутствующий спринт/наполнение и не является подтверждением завершения задачи.

После отдельного согласования схемы и apply Сергеем: применить новую миграцию
штатным процессом к локальной копии, затем выполнить:

```sh
AUDIO_SPRINT_APPLY_CONFIRM=sergey-approved-local-copy \
  node scripts/audio-sprint-general-release.mjs --execute --apply > /tmp/osen-apply.jsonl
node scripts/audio-sprint-general-release.mjs --execute > /tmp/osen-after.json
```

Apply выводит три JSON-строки: аудит до изменения, `transferred` с query_ids,
аудит после. В аудитах есть considered, already_in_base, eligible,
already_general, needs_review, protected, категории и все строки с sprint_id,
query_id, названиями, бронями/author_id/product_id. Файлы содержат служебные
идентификаторы и должны храниться в закрытом доступе.

Данный инструмент не применяет production-изменения. Релизная процедура и
любое применение к рабочей БД согласуются отдельно; перед новым кодом должна
быть установлена новая колонка, иначе запросы спринта вернут ошибку схемы.
