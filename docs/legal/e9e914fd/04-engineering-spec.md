# 04. Спецификация и чек-лист для разработки

Статус: спецификация. **В этом PR кода нет.** Реализация – отдельными PR после решения Сергея (вопросы в `05-open-questions.md`). Изменения воронок MAX Поток / BotHelp / MAX и живых текстов – только с отдельного разрешения.

## 1. Принцип: одно согласие на человека (account-level)

Повторяем паттерн AudioLad для Авторских условий (миграция `20270110120000_author_terms_account_level_acceptance.sql`, п. 28.2 Соглашения): юридическое принятие фиксируется **на аккаунт / субъекта**, одно принятие покрывает все текущие и будущие кабинеты. Для согласия на ПДн:

- Ключ субъекта – **человек**, а не кабинет автора и не workspace MAX Поток:
  - для MAX: `max_user_id` (глобальный идентификатор пользователя MAX);
  - для AudioLad: `auth.users.id`, если аккаунт связан;
  - связь двух идентичностей – через существующие `external_identities` / `max_auth_handoffs` (если используется), без новых догадок.
- Ключ оператора – `operator_key = 'ip-petrov'` (один оператор). Согласие не привязывается к `author_id`, `workspace_id`, `flow_id`.
- **Никогда** не создавать запись согласия на каждый кабинет автора или workspace. Чтение «есть ли согласие» – по субъекту + документу + действующей редакции.
- Отзыв тоже на уровне субъекта: отзыв в любом чате отзывает согласие целиком.

## 2. Данные

Предлагаемые таблицы (где именно – AudioLad Supabase или БД MAX Поток – решает Сергей, вопрос 5; рекомендация – там, где принимается callback, т. е. MAX Поток, с последующей синхронизацией в AudioLad при необходимости):

`pd_consent_documents`
- `id uuid pk`, `document_key text` (`photo-diagnosis-consent`), `version text`, `content_hash text` (sha256 опубликованного текста, `^[0-9a-f]{64}$`), `published_at timestamptz`, `is_current boolean` (уникальный частичный индекс по `document_key where is_current`), `requires_reconsent boolean`.

`pd_consents` (только вставка; append-only)
- `id uuid pk`, `operator_key text`, `document_id uuid fk → pd_consent_documents`, `subject_max_user_id bigint null`, `subject_user_id uuid null`, CHECK хотя бы один не null;
- `action text check in ('accept','decline','withdraw')`;
- `occurred_at timestamptz default now()`;
- `channel text` (`max`, `web`), `source_inbound_update_id uuid null`, `bot_connection_id uuid null`, `flow_id uuid null`, `flow_step_id uuid null` – только для аудита, **не** для области действия;
- `acceptance_text text not null` (текст кнопки/фразы);
- без IP/user-agent для MAX (их нет); для web – как в `author_terms_acceptances` (`ip_address inet`, `user_agent text <= 512`).

Функция чтения: `pd_consent_state(subject) → accepted_current | withdrawn | none` – последняя запись по субъекту и `document_key`; редакция действует, если она текущая или предыдущая без `requires_reconsent`.

RLS: запись и чтение только service role; в интерфейсе автора – только статус «согласие есть / нет / отозвано» и дата, без чужих данных.

## 3. Поток в боте (будущий PR, не сейчас)

1. Шаг «Согласие» перед шагом «Пришлите фото» (тексты – `03-client-message-draft.md`).
2. Callback `pd_photo_consent:accept:<version>` → запись `accept` → продолжить воронку. `decline` → запись `decline`, фото не запрашивать.
3. Входящее фото при `pd_consent_state != accepted_current` → не пересылать автору, ответить сообщением 3, удалить вложение из хранилища MAX Поток (см. 4).
4. Текст «Отзываю согласие» (и кнопка в меню) → запись `withdraw`, сообщение 4, постановка задачи на удаление.
5. Идемпотентность: повторный callback не создаёт вторую запись `accept` той же редакции (уникальность по subject + document + action + `source_inbound_update_id`).

## 4. Хранение и удаление

- `inbound_updates.raw_payload` (MAX Поток): сейчас хранится бессрочно. Нужно: для update с вложениями-изображениями – после обработки заменять вложения и текст на маркер (`{"redacted": true}`) не позже N дней (предложение – 30), сохраняя `dedupe_key`, тип, время. Отдельная задача, требует миграции и проверки дедупликации.
- Входящие фото не копировать в `media_assets` (сейчас и так не копируются – сохранить это поведение тестом).
- AudioLad `personal_materials`: при удалении по отзыву – **удалять файлы** PDF/аудио из bucket `personal-materials`, не только ставить `deleted_at` (сейчас soft delete файлы не трогает). Имя и фамилию клиента – обезличить.
- Плановая очистка фото: задача (cron/pg-boss) удаляет фото через 30 дней после выдачи результата. Журнал удаления: id записи, время, причина, без содержимого.
- Отзыв: удаление в течение 30 дней (ст. 21 ч. 5 152-ФЗ), исключения – оплата и сама запись `pd_consents`.
- Ответ на запрос субъекта – 10 рабочих дней: нужна выгрузка «что о человеке хранится» по `max_user_id` (contacts, events, inbound_updates, personal_materials).

- [ ] Отзыв в одном месте отзывает везде; тест.

- [ ] Повторный callback идемпотентен; тест.
- [ ] Редакция с `requires_reconsent` снова запрашивает согласие; тест.
