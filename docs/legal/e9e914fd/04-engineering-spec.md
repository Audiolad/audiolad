# 04. Спецификация и чек-лист для разработки

Статус: спецификация. **В этом PR кода нет.** Реализация – отдельными PR после решения Сергея (вопросы в `05-open-questions.md`). Изменения воронок MAX Поток / BotHelp / MAX и живых текстов – только с отдельного разрешения.

## 0. Текущий процесс (ответы Сергея 29.10.2026)

Фото приходят в **личные сообщения Сергея в MAX и Telegram**, не боту и не через сайт. Зоя тоже смотрит фото. Нейросети и зарубежные сервисы не используются. Поэтому сейчас:

- автоматической записи согласия нет; фиксация – ответ «Согласен(на)» в чате + строка в ручном журнале согласий (поля – `03-client-message-draft.md`). Журнал хранить в РФ, доступ – только Сергей и Зоя; где именно – вопрос 5;
- удаление фото через 30 дней – вручную в чатах (у Сергея и у Зои) и на телефонах, если фото сохранялись; в журнале – дата удаления;
- разделы 1–3 ниже – на случай, если согласие (или вся диагностика) переедет в бота MAX Поток или на сайт. Принцип одного согласия на человека действует и для ручного журнала.

## 1. Принцип: одно согласие на человека (account-level)

Повторяем паттерн AudioLad для Авторских условий (миграция `20270110120000_author_terms_account_level_acceptance.sql`, п. 28.2 Соглашения): юридическое принятие фиксируется **на аккаунт / субъекта**, одно принятие покрывает все текущие и будущие кабинеты. Для согласия на ПДн:

- Ключ субъекта – **человек**, а не кабинет автора и не workspace MAX Поток:
  - для MAX: `max_user_id` (глобальный идентификатор пользователя MAX);
  - для Telegram: `telegram_user_id`;
  - для AudioLad: `auth.users.id`, если аккаунт связан;
  - связь двух идентичностей – через существующие `external_identities` / `max_auth_handoffs` (если используется), без новых догадок.
- Ключ оператора – `operator_key = 'ip-petrov'` (один оператор). Согласие не привязывается к `author_id`, `workspace_id`, `flow_id`.
- **Никогда** не создавать запись согласия на каждый кабинет автора или workspace. Чтение «есть ли согласие» – по субъекту + документу + действующей редакции.
- Отзыв тоже на уровне субъекта: отзыв в любом чате отзывает согласие целиком.

## 2. Данные

Предлагаемые таблицы (где именно – AudioLad Supabase или БД MAX Поток – решает Сергей, вопрос 5; рекомендация – там, где принимается callback, т. е. MAX Поток, с последующей синхронизацией в AudioLad при необходимости):

`pd_consent_documents`
- `id uuid pk`, `document_key text` (`photo-diagnosis-consent`), `version text`, `content_hash text` (sha256 опубликованного текста, `^[0-9a-f]{64}$`), `published_at timestamptz`, `is_current boolean` (уникальный частичный индекс по `document_key where is_current`), `requires_reconsent boolean`.

`pd_consents` (только вставка; append-only)
- `id uuid pk`, `operator_key text`, `document_id uuid fk → pd_consent_documents`, `subject_max_user_id bigint null`, `subject_telegram_user_id bigint null`, `subject_user_id uuid null`, CHECK хотя бы один не null;
- `action text check in ('accept','decline','withdraw')`;
- `occurred_at timestamptz default now()`;
- `channel text` (`max`, `telegram`, `web`, `manual`), `source_inbound_update_id uuid null`, `bot_connection_id uuid null`, `flow_id uuid null`, `flow_step_id uuid null` – только для аудита, **не** для области действия;
- `acceptance_text text not null` (текст кнопки/фразы);
- `consent_basis text check in ('self','legal_representative','third_adult_own','third_adult_confirmed_by_sender')` – кто дал согласие (сам человек, законный представитель ребёнка, сам третий взрослый, подтверждение отправителя);
- без IP/user-agent для MAX (их нет); для web – как в `author_terms_acceptances` (`ip_address inet`, `user_agent text <= 512`).

Функция чтения: `pd_consent_state(subject) → accepted_current | withdrawn | none` – последняя запись по субъекту и `document_key`; редакция действует, если она текущая или предыдущая без `requires_reconsent`.

RLS: запись и чтение только service role; в интерфейсе автора – только статус «согласие есть / нет / отозвано» и дата, без чужих данных.

## 3. Поток в боте (только если диагностика переедет в бота; будущий PR, не сейчас)

1. Шаг «Согласие» перед шагом «Пришлите фото» (тексты – `03-client-message-draft.md`).
2. Callback `pd_photo_consent:accept:<version>` → запись `accept` → продолжить воронку. `decline` → запись `decline`, фото не запрашивать.
3. Входящее фото при `pd_consent_state != accepted_current` → не пересылать автору, ответить сообщением 3, удалить вложение из хранилища MAX Поток (см. 4).
4. Текст «Отзываю согласие» (и кнопка в меню) → запись `withdraw`, сообщение 4, постановка задачи на удаление.
5. Идемпотентность: повторный callback не создаёт вторую запись `accept` той же редакции (уникальность по subject + document + action + `source_inbound_update_id`).

## 4. Хранение и удаление

**Находка (подтверждена Сергеем): MAX Поток хранит полное тело каждого входящего сообщения бессрочно** – `inbound_updates.raw_payload`, без срока и удаления в коде. Фото для диагностики идут в личные сообщения, а не боту, но в боте всё равно остаются имена, тексты и вложения, которые присылают люди.

Рекомендация (отдельная задача, **в этом PR кода нет**):

- ввести срок хранения для `raw_payload`: после обработки и не позже N дней (предложение – 30) заменять текст и вложения маркером `{"redacted": true}`, сохраняя `dedupe_key`, тип события и время – чтобы не сломать дедупликацию;
- до включения – dry-run с подсчётом записей; миграция expand-only с rollback;
- входящие фото не копировать в `media_assets` (сейчас не копируются – закрепить тестом);
- выгрузка «что о человеке хранится» по `max_user_id` (contacts, events, inbound_updates) – для ответа на запрос в течение 10 рабочих дней;
- удаление по отзыву согласия – в течение 30 дней (ст. 21 ч. 5 152-ФЗ), исключения – сведения об оплате и сама запись о согласии.

Сроки по диагностике (согласовано Сергеем): фото – 30 дней после выдачи результата; результат – не дольше 3 лет. Срок хранения записи о согласии – предложение 3 года после отзыва, не подтверждено.

Вне этой задачи: AudioLad «Персональные материалы» – отдельный процесс со своим согласием, к диагностике по фото не относится (побочная заметка – `01`, раздел 5).

## 5. Чек-лист для PR реализации

- [ ] Согласие хранится на субъекта (MAX user / AudioLad user), не на кабинет автора / workspace; тест: два workspace, одно согласие – оба видят `accepted_current`.
- [ ] Отзыв в одном месте отзывает везде; тест.
- [ ] Запись append-only, есть версия и sha256 текста; тест на неизменяемость (нет UPDATE/DELETE для ролей приложения).
- [ ] Фото до согласия не доходит до автора и удаляется; тест.
- [ ] Повторный callback идемпотентен; тест.
- [ ] Редакция с `requires_reconsent` снова запрашивает согласие; тест.
- [ ] Очистка `raw_payload` с вложениями по сроку; dry-run с подсчётом до включения.
- [ ] `consent_basis` заполняется для фото ребёнка и другого взрослого; тест.
- [ ] Telegram и MAX одного человека не создают двух «разных» согласий, если идентичности связаны; иначе – два субъекта, без догадок.
- [ ] Видимые тексты: только короткое тире «–», длинное тире (U+2014) запрещено; без ссылок на сторонние сайты (кроме `{{CONSENT_URL}}`).
- [ ] Никаких фото, аудио, секретов и ПДн клиентов в репозитории и тестовых фикстурах (публичный репозиторий).
- [ ] Миграции – expand-only, с rollback SQL; production не применять без отдельного OK.
- [ ] Включение шага в живую воронку – отдельное решение Сергея (не в PR реализации).
