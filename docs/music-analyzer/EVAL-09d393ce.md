## Стенд

`node scripts/evaluate-music-features.mjs <manifest.json> <output-dir> --ids=<id1,id2> [--measure]`

Стенд читает только локальные файлы. Максимум 10 записей за запуск; никаких обходов каталога, сетевых URL, записей в БД и вызовов моделей/API. Для настоящего сравнения `before` и `after` – JSON-экспорты двух прогонов того же SHA256. Если after не задан, стенд явно повторно применяет только новый адаптер к before; такой результат не доказывает улучшение самой ML-модели. `--measure` дополнительно выполняет один локальный проход установленного ffmpeg на выбранном аудио.

Пути `audio`, `before`, `after` разрешаются относительно манифеста; можно использовать абсолютные локальные пути. Исходный и новый экспорт обязаны содержать совпадающий `sha256`; неподтверждённые права/разметка/файлы дают pending, несовпадающая идентичность даёт ошибку.

Пример запуска после заполнения локальной копии манифеста:

```bash
node scripts/evaluate-music-features.mjs /tmp/coffee-reference.json /tmp/coffee-eval --ids=aurafon-quiet-harmony,jazz-relax --measure
```

Выходы: `evaluation.json` с исходными/новыми прогнозами, признаками и статусами каждого поля; `evaluation.md` с перечнем проверенных и ожидающих записей. `totals.before/after` считает match/error/abstained/unlabelled отдельно. Baseline читает уже существующие `vocal.type` и pulse diagnostics, даже если UI их не показывал. Для обоих этапов одинаковы top-k: 3 жанра/стиля, 5 настроений, 10 инструментов. Для наборов меток сохраняются false_positive и missed; для энергии – расстояние до референсного диапазона. Для BPM – абсолютная ошибка и half/double error, совпадение только в пределах 4%, а не автоматическое принятие двойного темпа. Отказ от определения жанра не превращается в правильную классификацию.

## «Тихая гармония»

Проверять нужно не только coarse genres, но прежде всего styles: Dark Jazz находится именно в styles закреплённой таксономии. Сохранить старый экспорт с названиями, average/max и сегментными scores. После запуска сверить:

1. Сохранился ли исходный автоматический результат в raw и старых normalized-полях.
2. Удержан ли Dark Jazz в новом блоке; нет ли автоматической подстановки Ambient по названию/автору.
3. Остались ли альтернативы tempo `/2`, исходный и `×2`, а также Python octave scores; при слабом пульсе не появился ли выбранный BPM.
4. Соответствуют ли вокал/речь и инструменты полному прослушиванию, а не только трём CLAP-сегментам.
5. Как соотносятся энергия и динамика с референсами; не принята ли техническая громкость за настроение.

В синтетическом тесте с единственным неверным Dark Jazz получается «ошибка → отказ от утверждения», а не «ошибка → доказанный Ambient». Политика удержания намеренно может скрыть настоящий Dark Jazz до ручного подтверждения. Это явный компромисс, а не исправленная модель жанров.

## Версии, поправки и повтор анализа

`analysis_features_v1` содержит `schema_version=audiolad-features:1`, `calibration_version=conservative:1`; локальные формулы – `audiolad-dsp:1`. Старая энергия 0–1 не масштабируется на месте. Model version включает commit, checkpoint и его SHA256; численные scores и строковые confidence исходного анализатора не заменяются выдуманными вероятностями. Полные метаданные ML-признаков доступны в JSON; поля карточек показывают неизвестную confidence явно.

Owner/admin API:

- `GET /api/music-analyzer/runs/<id>/features` – automatic, effective и журнал поправок с автором, временем и причиной;
- `POST` на тот же путь – `{patch: {energy_0_100: 40}, reason: "..."}`; null для выбранного ключа возвращает его автоматическое значение;
- `POST /api/music-analyzer/runs/reanalyze` – `{requestId: <UUID>, runIds: [<UUID>, ...]}`. Максимум 10, список проверяется до постановки. Повтор того же requestId для тех же source IDs использует те же новые run IDs. Частичные ошибки возвращаются по каждому файлу; повторять безопасно с тем же requestId.

POST требует сессионную роль owner/admin и совпадающий Origin. UI лаборатории даёт ручную поправку, основание и повтор одного файла. Новый прогон получает новую версию, старые sealed строки не меняются. Поправки привязаны к конкретному прогону, не переносятся автоматически в новый; независимые ключи складываются по журналу, для одного ключа действует последняя записанная поправка. Журнал читается постранично, после 10 000 строк отказывает явно, не обрезает историю молча.

Поправка не переписывает базовый sealed паспорт, существующий альбом, описание или кофейные рекомендации. Для потребителя, которому нужны поправки, предназначен ответ effective. Старые экспорты намеренно содержат автоматику, журнал выгружается через features API. В новом `music_passport_attributes` CLAP-теги остаются interpreted с confidence=null; старые версии читаются как прежде. Полный блок хранится в прогоне, доступном по analyzer_run_id, без увеличения `structured_fields` сверх существующего лимита.
