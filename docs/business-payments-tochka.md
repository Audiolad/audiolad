# Оплата «АудиоЛад Бизнес» через Точку

План. Кода оплаты здесь нет. Миграции не написаны и никуда не применялись.
К Точке и к любому платёжному адресу запросы не отправлялись.
Секреты, токены и значения переменных окружения в этот файл не входят.

Условия от владельца: **30 дней бесплатно, все функции кабинета, карта не нужна; затем 799 ₽ в месяц.**

Решение Сергея **2026-10-28 14:47**: оплата ручная, раз в месяц, карта или СБП, той же ссылкой Точки.
Автосписания нет. После конца подарка или `paid_until` без оплаты музыка играет ещё **3 дня**, потом останавливается.
Кабинет и данные остаются. В эти 3 дня в кабинете виден баннер и прямая кнопка «Оплатить».
Напоминания и в кабинете, и письмом на почту аккаунта владельца (служебное письмо, не рассылка).
Миграция платёжных таблиц одобрена, только добавления. Подробности в разделах 3, 4 и 9.

Один успешный платёж = один оплаченный период 30×24 часа за 799 ₽.
Три дня музыки после конца в `paid_until` не записываются: это отдельное окно плеера.

Цена уже лежит в `src/lib/business/plan.ts`: `BUSINESS_PLAN_MONTHLY_PRICE_RUB = 799`.
В заказе это **79900 копеек**, валюта `RUB`. Цифру задаёт сервер. Клиент её не присылает.

## 1. Как сейчас платят за продукты

Покупатель уже вошёл в аккаунт. Сервер создаёт строку `orders` и строку `payments`
(`provider = tochka`, статус `pending`) и вызывает Точку.

| Шаг | Где |
| --- | --- |
| Создание ссылки | `src/lib/payments/tochka-client.ts` → `POST /acquiring/v1.0/payments` или, если включены чеки, `POST /acquiring/v1.0/payments_with_receipt` |
| Общая обвязка заказа | `src/lib/payments/start-tochka-checkout.ts` |
| Старый вход для покупки практики | `src/app/api/payments/route.ts` |
| Вебхук | `POST /api/webhooks/tochka` (`src/app/api/webhooks/tochka/route.ts`) |
| Проверка подписи | `src/lib/payments/tochka-webhook.ts`, JWT RS256, открытый ключ Точки |
| Зачисление | SQL `fulfill_tochka_payment_transactional` (последняя версия в `supabase/migrations/20261008120000_author_project_capacity_purchase.sql`) |
| Регистрация вебхука у банка | `scripts/register-tochka-webhook.mjs`, событие `acquiringInternetPayment`, адрес `https://audiolad.ru/api/webhooks/tochka` |

Ссылка на оплату одноразовая. `paymentLinkId` = `orders.id`.
В теле платежа: сумма в рублях, назначение до 140 символов, `consumerId` = id пользователя,
`redirectUrl` и `failRedirectUrl` на `{сайт}/checkout/result` с подписанным токеном заказа.
Режимы оплаты по умолчанию: карта и СБП (`card`, `sbp`).

Имена настроек, без значений: `TOCHKA_JWT_TOKEN`, `TOCHKA_CUSTOMER_CODE`,
`TOCHKA_CLIENT_ID`, `TOCHKA_MERCHANT_ID`, `TOCHKA_API_BASE_URL`,
`TOCHKA_PAYMENT_MODES`, `TOCHKA_USE_RECEIPT`, `TOCHKA_TAX_SYSTEM_CODE`,
`TOCHKA_RECEIPT_VAT_TYPE`, `TOCHKA_RECEIPT_PAYMENT_METHOD`,
`TOCHKA_RECEIPT_PAYMENT_OBJECT`, `NEXT_PUBLIC_SITE_URL`.

Если `TOCHKA_USE_RECEIPT` не равен `true` или не заданы система налогообложения и ставка НДС,
клиент Точки не собирается. Чек тогда не уходит. Для чека код принимает только
`paymentObject = service` и `paymentMethod = full_payment`. Другие значения
выключают всю оплату, не только Бизнес.

Вебхук:

- чужая подпись → ответ 400, деньги не зачисляются;
- событие пишется в `payment_webhook_events`, ключ повтора уникален
  (`transactionId`, иначе тип + operationId + статус + сумма);
- обрабатывается только `acquiringInternetPayment` со статусом `APPROVED`;
- `customerCode` и, если задан, `merchantId` сверяются с настройками;
- сумма и валюта вебхука должны совпасть с заказом, иначе `requires_review`, доступ не выдаётся;
- повтор того же события доступ второй раз не выдаёт;
- возвраты — отдельная ветка, этот план её не трогает.

Виды заказов сейчас: `product_purchase`, `course_upgrade`, `studio_music_license`,
`author_project_capacity`. У первых трёх обязательна практика. У пакета проектов
практики нет, и это продажа платформы, не автора.

После успешной оплаты:

- автору уходит письмо о продаже, только если у заказа есть `author_id_snapshot`
  (`enqueue_author_sale_email`);
- Сергею уходит письмо о продаже на адрес из `PLATFORM_OWNER_SALE_EMAIL`
  (`src/lib/payments/notify-platform-owner-sale.ts`), кроме тестовых платежей;
- в админке «Продажи» (`/admin/sales`) виден каждый успешный нетестовый `payments`
  вместе с названием из `practice_title_snapshot` и покупателем из профиля;
- своего письма покупателю с чеком АудиоЛад не шлёт. Чек 54-ФЗ, когда он включён,
  отправляет партнёр Точки на `Client.email`.

Книга автора (`ensure_author_sale_accrual`) при пустом `author_id_snapshot`
останавливается в `requires_review` с кодом `author_snapshot_missing`.
Для подписки Бизнеса так делать нельзя: иначе каждая оплата 799 ₽ попадёт
в очередь «разобрать вручную», хотя автора у этой продажи нет.
В миграции такое начисление нужно явно пропускать (`skipped`), как платформенную продажу.

В коде нет вызовов `/acquiring/v1.0/subscriptions` и `/acquiring/v1.0/subscriptions_with_receipt`.
Сохранённой карты и автосписания тоже нет.

## 2. Как сейчас устроен пробный период

Один модуль, задачи ba344b7f и 1e008ee8. Описание: `docs/business/access-grants.md`.
Миграция `supabase/migrations/20270120120000_access_grants_and_workspace.sql`
должна уже быть применена до оплаты. Этот план её не повторяет и правила подарка не меняет.

- Подтверждённая почта получает один период **30×24 часа**. Карта не спрашивается, списания нет.
- Часы запоминаются по хешу почты и по id пользователя (`access_grants`, вид `business_new_client`).
  Повторная регистрация того же адреса период не начинает заново.
- Оплаченный срок лежит отдельно, в `access_paid_periods.paid_until`.
  Новая дата записывается только если она позже уже сохранённой.
  Строка подарка при оплате не удаляется и не укорачивается.
- Пока `paid_until` ещё впереди, второй подарок не выдаётся.
- В момент `now >= ends_at` и без живой оплаты режим становится `offer`:
  полный плеер закрыт, кабинет, подборка и настройки остаются.
  Точной дополнительной отсрочки нет: граница включена в «уже закрыто»
  (`isPeriodActive` в `src/lib/access-grants/policy.ts`).
- Кнопка «Оформить подписку» только пишет событие `subscription_go_to_payment`
  и говорит, что деньги не списываются (`BusinessHomeAccessCard`).
  Платёжной ссылки она не создаёт.
- События (`trial_started`, дни 7/14/30, показ оферты, переход к оплате, продление)
  пишутся в `access_grant_events`, когда человек открывает кабинет.
  Это не письма и не расписание. Писем «скоро закончится» нет.
- `subscription_renewed` пишется один раз на адрес. Журналом каждого месяца он не служит.

Плеер кабинета берёт аудио из `/api/business/workspace/track-url`.
Сервер пускает звук только при режиме `trial` или `paid` и открытом направлении
(`workspacePlayerOpen`). У каждого трека `playableUntil` равен концу периода.
Плеер останавливает уже начатый звук в эту секунду и новый старт не подписывает.
Гостевая кофейня (`/guest/coffee`) — отдельный просмотр без аккаунта и без этих 30 дней.
Подписка её не включает и не выключает.

Старый пилот `/api/business/player/*` проверяет допуск пилота, а не эти часы.
Оплата не должна оставлять точку на этом пути звучать после конца периода аккаунта.
В рабочем PR любая выдача аудио точки сверяется с тем же окном аккаунта.

Генерация в Студии в подарок не входит. Это уже написано в правилах кабинета
(`businessGiftRulesText`). Подписка 799 ₽ открывает тот же плеер, что и подарок.
Безлимитную Студию она не добавляет.

## 3. Как подключить 799 ₽: разовый месяц, без автосписания

Каждый месяц владелец сам нажимает оплату. Сервер создаёт новый заказ на 79900 копеек,
Точка выдаёт обычную ссылку (карта и СБП, как у продуктов), вебхук `APPROVED`
один раз продлевает `paid_until`.

Так уже устроены и банк в нашем коде, и часы доступа:

- пробные 30 дней идут без карты, автосписание в конце подарка противоречит этому условию;
- СБП остаётся, как в текущей оплате;
- возврат идёт текущим контуром возвратов Точки для разового платежа;
- новый вебхук у банка регистрировать не нужно: тот же `acquiringInternetPayment`;
- длина периода совпадает с подарком: **30×24 часа**, не «то же число следующего месяца».

Формула, один раз внутри транзакции зачисления, под тем же замком, что и подарок.
Повтор вебхука дату заново не считает:

```text
начало = самое позднее из (время успешной оплаты, конец ещё идущего подарка, уже записанный paid_until)
конец  = начало + 30×24 часа
paid_until = самое позднее из (старый paid_until, этот конец)
```

Оплата в середине подарка не съедает оставшиеся бесплатные дни: месяц прибавляется к концу подарка.
Оплата после конца, в том числе в три дня, когда музыка ещё играет, считается от времени оплаты.
Оставшиеся дни этого окна к новому месяцу не прибавляются.
Второй заказ того же пользователя, пока первый ещё `pending`, не создаётся.
`paid_until` – это конец оплаченного или подарочного срока. Три дополнительных дня к нему не пишутся.

Публичная документация Точки описывает отдельный продукт «подписки»
(`Create Subscription`, `Create Subscription With Receipt`,
обзор: <https://developers.tochka.com/docs/tochka-api/opisanie-metodov/podpiski-rekurrentnye-platezhi/>).
Наш код эти методы не вызывает. Если позже понадобится автосписание, владельцу
нужно сделать в банке отдельно, до любого кода:

1. Подключить в интернет-эквайринге именно подписки и убедиться, что у ключа API есть
   права `MakeAcquiringOperation`, `ReadAcquiringData`, `ReadCustomerData`.
2. Принять, что подписка Точки сейчас только с карты. СБП для неё в этой документации нет.
3. Выбрать один режим. Банк не принимает вместе флаг `recurring` и график `Options`.
   График: `period = Month`, число списаний `trancheCount` (для месяца не больше 84).
   Либо без графика: мы сами вызываем `Charge Subscription`, когда пора списать.
4. Смириться с ограничениями банка: ссылка на подключение живёт 168 часов;
   закончившуюся подписку продлить нельзя, только создать новую;
   возврат платежа по подписке в документации банка делается в интернет-банке, не нашим текущим возвратом.
5. Чеки — методом `subscriptions_with_receipt`, тем же партнёром фискализации.
6. После этого — отдельная задача на код, статусы подписки и отмену. В первые PR оплаты это не входит.

## 4. Конец пробы, 3 дня и неоплата

Решение Сергея 2026-10-28. Конец срока – более поздняя из дат подарка и `paid_until`.
Пока `now` меньше этой даты, плеер открыт, как сейчас.

| Момент | Что происходит |
| --- | --- |
| До конца срока | Плеер открыт. В кабинете виден срок. Письмо за 3 дня до конца – отдельный PR напоминаний |
| Ровно в конец срока и ещё 3×24 часа | Музыка продолжает играть. Кабинет показывает баннер: срок закончился, музыка остановится через оставшиеся дни, кнопка «Оплатить» ведёт сразу на оплату этого аккаунта (`https://business.audiolad.ru/#dostup`). Списания нет, карта не хранится |
| Когда прошли и эти 3 дня | Плеер закрывается, уже играющий звук останавливается, новая ссылка на файл не выдаётся. Кабинет, точки, подборка и настройки остаются |
| Оплата прошла | `paid_until` сдвигается по формуле из раздела 3. Три дня в эту дату не входят. Плеер снова открыт до новой даты |

События дней 7/14/30 письмами не являются: они пишутся только при открытии кабинета
и только пока подарок ещё открыт.

Напоминания, отдельный PR после кассы. Служебные письма, не рекламная рассылка.
Получатель – почта аккаунта владельца. Точка и плеер в зале писем не получают и кнопку оплаты не показывают.

1. За 3 дня до конца срока.
2. В день конца срока: музыка ещё играет 3 дня, в письме прямая ссылка «Оплатить».
3. В окне этих 3 дней, за день до остановки: завтра музыка остановится, снова прямая ссылка «Оплатить».

Текст «деньги не списываются» меняется в PR кабинета, где ссылка Точки уже создаётся.
До этого кнопка остаётся честной: ничего не списывает.
Ошибка, которая просит принять оферту или подключить точку, содержит прямую ссылку:
оферта `https://business.audiolad.ru/documents/b2b-terms`, подключение точки `https://business.audiolad.ru/onboarding`.

## 5. Кто платит

Платит аккаунт владельца организации: пользователь `auth.users`, у которого в
`business_organization_members` роль `owner`.

- Заказ пишется на `orders.user_id` этого человека. `consumerId` платёжной ссылки — он же.
- Чек уходит на подтверждённую почту этого аккаунта.
- Часы доступа (`access_grants`, `access_paid_periods`) тоже на этот аккаунт
  (хеш почты + id). Одна оплата открывает кабинет и все его точки.
  Отдельной цены «за точку» и отдельного плательщика на устройство нет.
- Менеджер (`role = manager`) ссылку на оплату не создаёт.
- Сессия точки не платит. У плеера точки свой секрет устройства
  (`business_players` / `business_player_credentials`, код `AL-P-…`).
  Это не пользователь. Методы сердцебиения и учёта проигрывания заказ не создают
  и Точку не вызывают. В рабочем PR у этих маршрутов не появляется импорта оплаты.
- Если владелец вошёл в браузер на компьютере в зале, платит всё равно его аккаунт,
  не устройство. Проверка на сервере: роль `owner`, а не «кто-то открыл плеер».
- Режим сопровождения, как и у авторских документов, согласие и оплату записать не может.

Доступ к заказам: владелец читает только свои `orders` (политика SELECT уже есть).
`payments` клиенту не отдаются, их пишет service role. Так остаётся.

Возврат после оплаты на `audiolad.ru/checkout/result` совместим с кабинетом:
в бою cookie сессии стоит на `.audiolad.ru` и виден на `business.audiolad.ru`.
Страница результата для этого вида заказа ведёт обратно в кабинет Бизнеса.
Второй адрес вебхука не нужен.

## 6. Чек 54-ФЗ и согласие с документами

Чек — тот же контур, что у продуктов.

- Тот же флаг `TOCHKA_USE_RECEIPT`, та же система налогообложения, та же ставка НДС.
  Новых имён настроек для Бизнеса нет.
- Позиция чека: услуга, одна штука, 799.00 ₽, название
  «АудиоЛад Бизнес – доступ на 30 дней». Способ расчёта остаётся `full_payment`,
  предмет — `service`. Иначе текущий разбор настроек отключает оплату целиком,
  включая продукты. Отдельный «предоплатный» чек только для Бизнеса в этот заход не делается:
  настройка одна на все платежи.
- `Client.email` — почта аккаунта владельца. Почта точки, если она вообще появится, в чек не подставляется.
- Тело чека, почта и данные карты в `payment_webhook_events` не пишутся.
  Журнал вебхука и сейчас выбрасывает эти поля (`src/lib/payments/webhook-ledger.ts`).

Согласие с офертой — один раз на аккаунт, по тому же правилу, что авторские условия
(решение 10.10.2026, повтор 18.10.2026, миграция
`20270110120000_author_terms_account_level_acceptance.sql`):
личное принятие владельцем аккаунта покрывает все его текущие и будущие пространства.
Для заведения это не таблица авторов. Тексты для клиента уже лежат как страницы
(`/documents/b2b-terms` и соседние), сохранённого «принято» у аккаунта заведения нет.

Новая строка — одна на аккаунт, до первой платёжной ссылки:

- документ: текущая редакция условий Бизнеса (`b2b-terms`), с версией и хешем текста;
- кто нажал = id этого же аккаунта;
- нет `location_id` и нет `player_id`: вторая точка и вторая организация того же владельца
  кнопку второй раз не показывают;
- подарок по-прежнему начинается без карты и без списания;
- новая редакция текста сама старое согласие не подменяет. Нужно ли спрашивать снова,
  решает владелец с юристом отдельной задачей.

Авторское единое соглашение (принятие автором, чтобы его музыка могла попасть в Бизнес)
этим согласием заведения не заменяется. Это другой человек и другая таблица.

| `ensure_author_sale_accrual` | Для этого вида исход `skipped`, не `requires_review` |
| `fulfill_tochka_payment_transactional` | Ветка вида: не выдаёт практику и не выдаёт слоты проектов; один раз записывает период и двигает `paid_until` |
| Индекс | Не больше одного `pending` заказа `business_subscription` на `user_id` |

Новые таблицы. RLS включён. `anon` и `authenticated` без прав.
Пишет service role. У периода нет внешнего ключа на `auth.users`, как у часов подарка:
удаление аккаунта не должно стирать уже оплаченный срок и давать тот же адрес заново.

`business_subscription_periods` — один оплаченный месяц на заказ:

- `order_id` уникален и ссылается на `orders` (при удалении заказа строка не исчезает: `ON DELETE RESTRICT`);
- `user_id`, `email_hash` (64 hex), `kind = business_new_client`;
- `period_start`, `period_end` (`period_end > period_start`);
- `amount_minor = 79900`;
- время, когда вебхук применил строку.

Повтор `APPROVED` по тому же заказу находит эту строку и второй месяц не прибавляет.

`business_offer_acceptances` — одно согласие на аккаунт:

- первичный ключ `user_id`;
- `document_key`, `document_version`, `content_hash`, `accepted_at`;
- `accepted_by_user_id` равен `user_id`.

Запись согласия — функция SECURITY DEFINER: вызывающий равен этому пользователю,
у него есть роль `owner` хотя бы в одной его организации, режим сопровождения отказывается.
Прямой INSERT с клиента не выдаётся.

`access_paid_periods` и `access_grant_events` новыми колонками не обрастают.
Журнал денег — заказы, платежи и `business_subscription_periods`.

Откат, если эта миграция последняя и новые строки не нужны, описывается в файле миграции
командами `DROP` только новых объектов и возвратом проверок `order_kind` к предыдущему списку.
Откат не выполняется этим планом.

`docs/DATABASE.md` обновляется в PR миграции, когда объекты реально описаны файлом миграции.
Сейчас схему базы этот документ не меняет.

## 8. Вебхук, повторы, безопасность

- Адрес вебхука прежний. Новый тип события для разового месяца не нужен.
- Подпись RS256 проверяется до записи доверия. Неверная подпись не зачисляет оплату.
- Сумма вебхука обязана быть 79900 и `RUB`. Иначе `requires_review`, `paid_until` не двигается.
- `paymentLinkId` остаётся id заказа. Чужой `operationId` не приклеивается к другому заказу.
- Идемпотентность уже есть на платеже (`provider + provider_payment_id`, `provider + idempotency_key`)
  и на событии (`provider + dedup_key`). Период добавляет уникальность по `order_id`.
- Зачисление и сдвиг `paid_until` — одна транзакция. Падение посередине откатывает оба шага,
  событие остаётся на повтор, как у текущих продуктов.
- Клиент не называет сумму, длину периода и id организации чужого человека.
- Создание ссылки требует живую сессию владельца и уже сохранённое согласие аккаунта.
- Почта для чека берётся из подтверждённого аккаунта, не из тела запроса.
- Секреты Точки остаются в окружении сервера. В репозиторий, в журнал вебхука и в ответ браузеру они не попадают.
- Тестовый платёж (`is_test`) период кабинета не открывает.
