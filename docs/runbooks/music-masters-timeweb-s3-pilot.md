# Пилот `music-masters` в Timeweb S3

Статус: подготовлено, не активировано. Этот runbook не является разрешением
создавать платный бакет, менять production-переменные или переносить файлы.

## Безопасная модель

- `storage_bucket = music-masters` остаётся логическим именем.
- `storage_provider` выбирается для каждого `music_audio_assets`.
- Старые и новые строки по умолчанию используют `supabase_file`.
- S3 включается для новых загрузок только явным
  `MUSIC_MASTERS_UPLOAD_PROVIDER=timeweb_s3`.
- Копирование не переключает провайдер и не удаляет локальный оригинал.
- Cutover разрешён только после совпадения размера и SHA-256 обеих копий.
- Rollback сначала повторно проверяет локальный файл по SHA-256.

## 1. Подготовка в панели Timeweb Cloud

Выполнять только после отдельного согласования расходов.

1. Открыть **Объектное хранилище → Создать бакет**.
2. Выбрать приватный бакет класса **Standard**.
3. Для первого этапа выбрать регион **Санкт-Петербург** — тот же
   географический контур, что и текущий сервер. Не выбирать другой регион без
   отдельного замера задержки и стоимости трафика.
4. Задать отдельное непубличное имя бакета. Не использовать
   `music-masters` как признак публичности: это только имя.
5. Отключить публичный доступ и публичный листинг.
6. Включить шифрование на стороне сервиса, если этот переключатель доступен.
7. Включить lifecycle для незавершённых multipart-загрузок: удалять их через
   1 день. Lifecycle готовых объектов на удаление не задавать.
8. Версионирование на пилоте допустимо включить как дополнительную страховку.
   До массовой миграции задать срок хранения неактуальных версий, иначе
   занимаемый объём будет расти скрыто.
9. Создать отдельную пару S3-ключей только для АудиоЛада. Выдать ей доступ
   только к пилотному бакету и операциям чтения, записи, HEAD и удаления.
   Удаление нужно приложению для отменённых новых загрузок; миграционный
   скрипт локальные файлы не удаляет.
10. Скопировать из панели точные endpoint и код региона. Для Timeweb обычно
    используется endpoint `https://s3.twcstorage.ru`, но production должен
    получить значение из панели, а не из этого примера.

## 2. CORS бакета

Разрешить только production-origin и тестовый origin, который будет явно
согласован для пилота:

```json
[
  {
    "AllowedOrigins": ["https://audiolad.ru"],
    "AllowedMethods": ["GET", "HEAD", "PUT"],
    "AllowedHeaders": ["content-type", "x-amz-*"],
    "ExposeHeaders": ["etag", "content-length"],
    "MaxAgeSeconds": 3600
  }
]
```

Не добавлять `*` в `AllowedOrigins`. После настройки отдельно проверить
preflight `PUT` из кабинета автора.

## 3. Production-переменные

Значения хранить только в защищённом EnvironmentFile/секретах, не в Git:

```text
TIMEWEB_S3_ENDPOINT
TIMEWEB_S3_REGION
TIMEWEB_S3_ACCESS_KEY_ID
TIMEWEB_S3_SECRET_ACCESS_KEY
TIMEWEB_S3_MUSIC_MASTERS_BUCKET
TIMEWEB_S3_FORCE_PATH_STYLE
```

Опционально: `TIMEWEB_S3_SESSION_TOKEN`.

`MUSIC_MASTERS_UPLOAD_PROVIDER` сначала **не задавать**. Отсутствующее значение
означает `supabase_file` и сохраняет прежнее поведение.

## 4. Применение кода и схемы

1. Снять резервную копию БД штатным production-процессом.
2. Применить миграцию
   `20270411120000_music_master_storage_providers.sql`.
3. Убедиться, что все существующие master-строки получили
   `storage_provider = supabase_file`.
4. Развернуть код при незаданном `MUSIC_MASTERS_UPLOAD_PROVIDER`.
5. Проверить обычную загрузку, транскодирование, паспорт, Shazam и скачивание
   старого локального мастера.
6. Выполнить отчёт:

```bash
npm run music-storage:report
```

## 5. Формирование allowlist пилота

Пилот — 3–5 непублично-критичных мастеров разных размеров и форматов. Сначала
только dry-run:

```bash
npm run music-storage:pilot -- \
  --mode copy \
  --asset-id <uuid-1> \
  --asset-id <uuid-2>
```

Команда выводит точный список, пути и размеры. `--limit N` разрешён только для
подготовки списка (максимум 20), но для production-пилота следует повторить
команду с явными UUID.

## 6. Shadow copy

После проверки allowlist и отдельного разрешения:

```bash
AUDIOLAD_MUSIC_STORAGE_PILOT=1 \
npm run music-storage:pilot -- \
  --mode copy \
  --asset-id <uuid-1> \
  --asset-id <uuid-2> \
  --execute
```

Для каждого файла команда:

1. скачивает локальный объект во временный каталог с правами `0600`;
2. проверяет размер и вычисляет SHA-256;
3. загружает объект по тому же логическому пути в S3;
4. скачивает S3-копию и повторно вычисляет SHA-256;
5. фиксирует совпадение в `music_storage_copies`;
6. записывает SHA-256 в asset;
7. всегда удаляет только локальные временные файлы.

Повторный запуск безопасен: проверенная копия с тем же размером и хешем
пропускается. Исходный объект Supabase Storage не удаляется.

## 7. Canary cutover

Переключать по одному asset. Сначала dry-run, затем отдельное разрешение:

```bash
npm run music-storage:pilot -- --mode cutover --asset-id <uuid>

AUDIOLAD_MUSIC_STORAGE_PILOT=1 \
npm run music-storage:pilot -- --mode cutover --asset-id <uuid> --execute
```

После каждого UUID проверить:

- авторский preview и скачивание оригинала;
- транскодирование в `music-streams`;
- повторную обработку/анализ;
- паспорт и Shazam, если применимо;
- `npm run music-storage:report`;
- журнал приложения на `music_storage_*` и HTTP 4xx/5xx S3.

## 8. Rollback

Rollback не копирует данные обратно: локальный оригинал обязан оставаться на
месте. Команда повторно скачивает его, сверяет SHA-256 и лишь затем меняет
provider строки:

```bash
npm run music-storage:pilot -- --mode rollback --asset-id <uuid>

AUDIOLAD_MUSIC_STORAGE_PILOT=1 \
npm run music-storage:pilot -- --mode rollback --asset-id <uuid> --execute
```

Если локальный объект отсутствует или его хеш отличается, rollback
останавливается без изменения строки.

## 9. Новые загрузки через S3

Только после успешного canary:

1. временно задать `MUSIC_MASTERS_UPLOAD_PROVIDER=timeweb_s3`;
2. загрузить один новый WAV и один OGG;
3. проверить browser PUT/CORS, finalize, ffprobe, транскодирование,
   скачивание, анализ и отмену незавершённой загрузки;
4. при любой ошибке убрать переменную: новые загрузки снова пойдут в локальный
   provider, уже созданные строки продолжат читать свой per-asset provider.

## 10. Мониторинг

- `music_storage_daily_metrics`: запросы, оценка байтов и ошибки по provider и
  операции;
- `music_storage_copies`: статусы, число попыток, последняя безопасная ошибка;
- `music_storage_cleanup_jobs`: durable cleanup при удалении трека. `blocked`
  означает, что teardown не был подтверждён и удалять объект автоматически
  нельзя; `pending` означает подтверждённый teardown и неудачное удаление;
- `npm run music-storage:report`: объём/число assets по provider, копии и
  метрики за 30 дней;
- `audiolad-disk-health.timer`: корневой диск каждые 5 минут, warning 85%,
  critical 90%.

Метрика `sign_download` учитывает ожидаемый размер подписанного файла. Это
верхняя оценка исходящего трафика: клиент может скачать не весь объект. Для
счёта Timeweb использовать её вместе с фактической статистикой S3 в панели.

Повтор cleanup по `pending` сначала выполняется как dry-run:

```bash
npm run music-storage:cleanup
```

После проверки списка и отдельного разрешения:

```bash
AUDIOLAD_MUSIC_STORAGE_CLEANUP=1 \
npm run music-storage:cleanup -- --execute
```

Команда принципиально не обрабатывает `blocked`: такой job сначала требует
ручной проверки результата teardown.

## Стоп-факторы

- отсутствует точный allowlist;
- нет резервной копии БД;
- S3 credentials имеют доступ к другим бакетам;
- CORS содержит wildcard;
- SHA-256 или размер копии не совпадает;
- локальный оригинал отсутствует;
- ошибки S3 растут либо p95 download заметно хуже локального baseline;
- корневой диск достиг critical-порога.
