## 1. Словарь метрик (проверено по `admin_ratings_summary`, миграция `20260922120000`)

| Метрика на экране | Что это на самом деле | Формула / источник | Единица |
|---|---|---|---|
| **Оценки** (379) | Число **активных пар слушатель×продукт** с оценкой | `count(*) FROM practice_ratings WHERE excluded_at IS NULL AND created_at в периоде` | пара (user, product) |
| **Звёзды** (1890) | Сумма **текущих** звёзд этих пар | `sum(stars)` там же | звёзды |
| **Уникальные оценившие** (39) | Разные аккаунты среди этих пар | `count(DISTINCT user_id)` | аккаунт |
| **Eligible** (754) | Пары слушатель×продукт, где накоплено ≥30 с медиа-времени при легальном доступе | `count(*) FROM practice_listen_stats WHERE rating_eligible_at в периоде` | пара |
| **Eligible без оценки** (375) | Eligible-пары, у которых нет активной оценки | `eligible − rated_eligible` | пара |
| **Конверсия** (50%) | Доля eligible-пар, которые оценили | `rated_eligible / eligible` | доля пар |
| **Средняя** (4,99) | Только для админки | `sum(stars) / count(*)` | звёзд на пару |

Важные свойства, проверенные в коде:

* **Повторная оценка не создаёт новую строку.** `UNIQUE(user_id, practice_id)` плюс атомарный
  `set_practice_rating` (`SELECT … FOR UPDATE` и повтор при `unique_violation`). Изменение
  3→5 меняет сумму звёзд, а число оценок остаётся прежним. Повтор той же оценки ничего не пишет.
  Каждое изменение попадает в журнал `practice_rating_events`, «Оценки» его не считают.
* **Периоды 7/30 дней** берутся по `created_at`, то есть по времени **первой** оценки, а звёзды
  по **текущему** значению. Старая оценка, исправленная сегодня, в «7 дней» не попадает.
  Eligible в периоде считаются по `rating_eligible_at`.
* **Числители и знаменатели одной «единицы».** Конверсия считается по парам, а не по людям.
  39 человек — отдельная метрика, сравнивать её с 754 или 379 напрямую нельзя.

### Почему 754 − 375 = 379 при 39 уникальных

* `rated_eligible = 754 − 375 = 379`, ровно столько же, сколько оценок. Это **ожидаемо**:
  сервер принимает оценку только при `rating_eligible_at IS NOT NULL` для этой пары
  (`evaluatePracticeRatingGate`). Значит, у каждой оценённой пары есть eligible-строка.
  Сходство чисел — проверка целостности, а не аномалия.
* 39 — это люди, 379 — пары. В среднем **≈9,7 оценённых продукта на аккаунт**
  (379 / 39), а eligible-пар ≈19 на аккаунт.
* Расхождение было бы признаком проблемы только при `rated_eligible ≠ rating_count`:
  например, оценки без eligibility (обход гейта) или исключённые строки. Проверка R1 в пакете
  запросов.

### Что следует из средней 4,99

`1890 / 379 = 4,987`. Если бы все оценки были 5★, звёзд было бы `379 × 5 = 1895`. Недостаёт
**всего 5 звёзд**, поэтому **не-пятёрок не больше 5 из 379** (например, пять четвёрок или одна
тройка и одна четвёрка). Почти все оценки — пятёрки. Отсюда:

* **средняя по продукту почти не информативна**: у всех продуктов около 5,0. Исключение любой
  группы сигналов **почти не меняет среднюю**, но **сильно меняет число оценок**. Именно это
  поле влияет на будущие сортировки;
* картина «≈40 аккаунтов ставят по ~10 пятёрок» одинаково объясняется командой, авторами и
  друзьями проекта, оценивающими каталог, и накруткой. По одной средней их не различить.

## 2. Сигналы предупреждений: что именно считается

Источник — `admin_ratings_diagnostics`. Все сигналы считаются **за всё время**, независимо от
выбранного периода экрана, и только по `practice_ratings` с `excluded_at IS NULL`.

| Сигнал на экране | Точное определение | Как НЕ надо читать |
|---|---|---|
| «1 IP-сигнал на 38+ аккаунтов» | Есть 1 значение `vote_ip_hmac`, у которого ≥3 разных аккаунта, и у самой большой группы их 38. HMAC IP пишется **при первой оценке пары** и при правке не обновляется | Это не «38 мошенников» и не «38 фейков». Это 38 из 39 оценивших, то есть **почти все** |
| «1 device на 3+ аккаунтов» | 1 значение `device_id_hmac` (HMAC браузерного `audiolad_anonymous_id` из localStorage) у ≥3 аккаунтов | Это не отпечаток устройства: id живёт в браузере и **не меняется при смене аккаунта** |
| «9 быстрых цепочек < 10 мин» | 9 **пар** (user, product), где `регистрация ≤ eligibility ≤ оценка` и `оценка − регистрация ≤ 10 мин` | Это **пары, а не аккаунты**: один новый аккаунт за 10 минут может дать несколько пар |

### 2.1. «Один IP на 38 аккаунтов»: главная гипотеза — технический адрес прокси

Проверено по коду:

1. IP для HMAC берёт `getTrustedClientIp`: `X-Real-IP`, иначе **самый правый** хоп
   `X-Forwarded-For`, иначе `unknown`, и тогда HMAC = NULL.
2. В Next.js 16.3.4 (`node_modules/next/dist/server/base-server.js`, стр. 612) стоит
   `req.headers['x-forwarded-for'] ??= originalRequest.socket.remoteAddress`. Если nginx
   **не передаёт** `X-Real-IP`/`X-Forwarded-For` в `location`, который проксирует
   `/api/listen/.../rating` (или `/api/max/rating`), Next сам подставляет адрес TCP-соседа,
   то есть **127.0.0.1 самого nginx**. Тогда у **всех** слушателей один «IP», и сигнал
   выглядит ровно как на скриншоте: одна группа почти из всех оценивших.
3. В git есть только сниппеты upload-location, где заголовки выставлены. **Боевой vhost
   `audiolad.ru` в git не лежит** (это зафиксировано в `trusted-client-ip.ts` и
   `ZERO_DOWNTIME_DEPLOY.md`), поэтому основной `location /` из репозитория не проверить.
4. Тот же хелпер используют rate-limit аналитики (`/api/analytics/*`). Если гипотеза верна,
   эти лимиты тоже фактически общие на всех, а не «на клиента».

Альтернативные объяснения, от более к менее вероятным: (а) все оценки поставлены из одного
офиса или квартиры (команда/автор тестирует каталог); (б) мобильный CGNAT или общий VPN;
(в) реальная накрутка с одного адреса. **В пользу (1)/(а)** говорит то, что группа включает
38 из 39 оценивших: при накрутке «живые» оценщики остались бы вне группы.

Как подтвердить, ничего не меняя (нужно OK Сергея на read-only доступ к прод-хосту):
* посмотреть `nginx -T` и проверить, есть ли в `location /` директивы
  `proxy_set_header X-Real-IP $remote_addr` и `X-Forwarded-For $proxy_add_x_forwarded_for`;
* **или** в окружении приложения посчитать `hmacRatingSignal("ip", "127.0.0.1")` и
  `"::ffff:127.0.0.1"` и сравнить с доминирующим `vote_ip_hmac` (запрос S1 выдаёт только
  «совпало / не совпало», не сам HMAC).

Если подтвердится, исправление делается в nginx (передать заголовки) и отдельно согласуется.
Уже записанные `vote_ip_hmac` для анализа IP **непригодны**: их нельзя «починить» задним
числом, и **нельзя** использовать их как основание для каких-либо действий.

### 2.2. «Один device на 3+ аккаунтов»

`audiolad_anonymous_id` создаётся один раз на браузер и **переживает выход и вход в другой
аккаунт**. Три и больше аккаунтов в одном браузере — типичная картина для владельца или
тестировщика (и для `test-user-reset`), семьи на одном компьютере, администратора, который
«проверяет, как видит слушатель». Для MAX-оценок device пишется как NULL. Сигнал слабый и
годится только для ручного разбора.

### 2.3. «9 быстрых цепочек»

Порог eligibility — 30 с медиа-времени, и до него легально можно дойти через **превью каталога**
(`catalog_preview`, 30–90 с). Сценарий «пришёл по ссылке автора → зарегистрировался → послушал
30 с → поставил звезду» укладывается в 2–3 минуты и **нормален**. Сам по себе быстрый путь
ничего не доказывает. Он значим только **вместе** с общим device, одинаковым числом звёзд у
всех, ровно 30–35 с прослушивания и концентрацией на одном продукте или авторе. Это
показывает запрос S3.

## 4. Влияние на средние продуктов

Без живых данных можно сказать точно:
* средняя всех продуктов ≈5,0, поэтому **любое исключение почти не сдвигает средние**
  (максимальный общий сдвиг ограничен 5 «недостающими» звёздами);
* **сильно меняется количество**: если 38 из 39 аккаунтов вне подозрений (технический IP),
  количество не меняется; если бы IP-группа была реальной накруткой, у продуктов осталось бы
  по 0–1 оценке.

Запрос S4 в пакете считает по каждому продукту `count/avg` «как есть» и «без пар из каждой
группы сигналов» (имитация, **ничего не исключает**). Вывод — обезличенные `P01…`, названия
продуктов по желанию.
