# Спецификация: рейтинговые сортировки и фильтры каталога (проект, задача 612f9c76)

Статус: **ПРОЕКТ. Ничего не включено.** Публичная выдача каталога, расчёт публичного агрегата и
права оценивания не меняются. **Ни одна публичная сортировка не включается без отдельного
разрешения Сергея на релиз.**

Документ переписан 17.10.2026 по прямым решениям Сергея (Company Core, уточнения
168f6eed, 81b0add1, cb5aa442, 53ff0c99, a1fb3b67). Прежний вариант «Байес m₀ = 3,5, C = 10,
N_min = 10, фильтр score ≥ 4,3» **отменён** и в проекте не предлагается.

## 1. Утверждённые правила звёздного рейтинга продукта

1. **Балл = простая арифметическая средняя** всех учитываемых действительных голосов 1–5.
   Каждый голос имеет равный вес, единственный голос тоже считается.
2. **Рядом всегда показывается число голосов** (например, «5,0 · 3 оценки»).
3. **Нет минимального порога голосов**: ни для показа балла, ни для попадания в сортировку или
   фильтр. **Нет априорной оценки и усреднения к 3,5.**
4. **n = 0**: показывается «Пока нет оценок». Балл не равен 0 и не равен 3,5. В сортировке по
   оценке такие продукты идут **после всех оценённых** с прозрачным вторичным порядком (п. 4).
5. **При равной средней балл одинаковый**: число голосов балл не меняет, а влияет только на
   порядок как вторичный ключ.
6. **Какие голоса учитываются:**
   * оценки авторов на собственные продукты — **да**, на общих основаниях;
   * оценки после реального прослушивания бесплатного превью платного продукта (≥30 с) — **да**,
     без требования покупки. Право оценки не ужесточается без отдельного решения (разбор
     30/60/90-секундных превью при необходимости);
   * гостевые оценки — только после надёжной серверной верификации и поэтапного запуска за
     флагом ([`GUEST_RATINGS_ARCHITECTURE.md`](./GUEST_RATINGS_ARCHITECTURE.md));
   * тестовые и служебные аккаунты, **действительно помеченные** как test/staff, — отдельная
     маркированная категория. В органический рейтинг не входят, история не удаляется и массово
     не помечается `excluded_at`. Авторов как категорию не исключаем;
   * `excluded_at IS NULL`, как сейчас. Автоматически ничего не исключается.
7. Остальные показатели (уникальные слушатели, время, повторы) **не заменяют** звёздный рейтинг.
   Они дают **отдельные** сортировки.

## 2. Обязательные сегменты

Рейтинги не смешиваются. Минимум два независимых сегмента со своими выборками, распределениями
и сортировками:

| Сегмент | Что входит | Основные показатели |
|---|---|---|
| **«Музыка и звуки»** | музыкальные альбомы и треки, функциональные и фоновые звуки, природа, водопад, шумы (белый, пылесос и т. п.), звуковые ландшафты, пространство Ori | уникальные слушатели, осмысленные qualified plays, прослушанное время, возвраты в другие дни. Completion длинных лупов — осторожно, автоплей сам по себе не вознаграждается |
| **«Аудиопрактики и медитации»** | голосовые медитации, управляемые практики, программы (подтипы — будущие фильтры) | уникальные люди, доля дослушивания, возврат к практике в другие дни, звёздный рейтинг с числом голосов. Короткие практики не штрафуются за малое абсолютное время |

Внутри сегмента треки и продукты/альбомы/программы сравниваются **раздельно**. Авторский
рейтинг нормализуется по объёму каталога и охвату.

**Классификация (предложение mapping'а, ничего не переименовывается):**
* база — `practices.product_kind`: `music` → «Музыка и звуки», `practice` →
  «Аудиопрактики и медитации», `audio_post` → отдельно (в рейтинги каталога не входит, пока
  Сергей не решит иначе);
* подтип внутри «Музыки и звуков» (музыка / природа / шум / ландшафт) — из `format` и данных
  музыкального паспорта, **не** по user_id автора Ori: будущие авторы аналогичных звуков
  попадут в тот же сегмент;
* безопасное админское исправление ошибочной классификации — отдельным полем-override с
  журналом;
* смешанный релиз требует явной основной категории;
* тесты классификации: природные звуки, водопад, пылесос, white noise, музыка, голосовая
  практика, медитация, смешанный релиз.

## 4. Сортировка «По оценке» (проект)

* Ключ 1: средняя по убыванию; продукты с n = 0 — после всех оценённых.
* **Вторичный порядок (предложение, требует утверждения)**: число голосов ↓ → число уникальных
  слушателей с ≥30 с за 30 дней ↓ → дата публикации ↓ → `publication_id` (детерминированная
  пагинация). Для n = 0: дата публикации ↓ → `publication_id`.
* На карточке: «4,8 · 12 оценок» или «Пока нет оценок». Звёзды без числа не показываем.
* JSON-LD `AggregateRating` не добавляем до отдельного решения.

## 5. Другие публичные сортировки (только концепция, не запускать)

2–3 понятные сортировки внутри сегмента: «По оценке» (п. 4), «Часто слушают» (уникальные
слушатели с ≥30 с за 30 дней), «Популярные» (композит — только после отдельной методики на
реальных данных и утверждения весов Сергеем). Сложная внутренняя формула публично не
раскрывается.

## 6. Внутренняя админка «Рейтинги и популярность» (следующий этап, проект)

Переключатель [Музыка и звуки] / [Аудиопрактики и медитации]; периоды 7/30/90 дней и всё
время; тип сущности (трек / продукт / автор). Отдельные сортировки: по звёздам (средняя и
число), по уникальным людям, по qualified plays, по возвратам в другие дни, по прослушанным
минутам. Понятные русские определения. Просмотр конкретных оценивших с ФИО/email — только для
администраторов (вкладка «Оценки → Слушатели», PR #891).

**Данные, которые уже есть** (проверено на проде): `practice_listen_stats` — 955 пар
слушатель×продукт с 05.09.2026 (`real_listened_ms`, `rating_eligible_at`, только
зарегистрированные); `playback_usage_facts` — 365 639 сэмплов с 26.09.2026 (`listened_ms`,
`position_ms`, `phase` advance/seek/pause/ended/track_change, `playback_rate`, `user_id` или
`anonymous_id`/`visitor_key`, `audio_item_id`).

Из этих данных можно честно посчитать уникальных зарегистрированных слушателей, прослушанное
время, сессии по `listening_key` и возвраты по дням за период с 26.09. Для гостей
уникальность ограничена `anonymous_id`/`visitor_key`: это браузер, а не человек. Методика
qualified plays (≥30 реальных секунд, правило для коротких треков, исключение seek/retry/
autoplay-дублей) и лёгкие агрегаты (ежедневные роллапы, без тяжёлых запросов на каждый
просмотр) — отдельный документ следующего этапа. Веса композитов заранее не фиксируются.
Тест-кейсы: 1 слушатель × 10 против 10 × 1, 2 мин против 5 мин, луп и автоплей.

## 7. Набросок реализации «По оценке» (после разрешения)

* Лёгкий агрегат `practice_rating_aggregates(practice_id PK, rating_count, total_stars,
  organic_count, organic_total_stars, updated_at)`: обновление в `set_practice_rating` или
  периодический пересчёт; в листинге только join по PK. Раздельные all-data и organic-data
  (без помеченных test/staff).
* `CATALOG_SORTS += "top_rated"` с ключами из п. 4, сегмент — обязательный параметр.
* Публичный DTO: `ratingCount` и средняя с одним знаком; никаких id и email оценивших.
* Флаг окружения, по умолчанию выключен.
* Тесты: один голос 5★ против многих 4,8★ (балл не корректируется, порядок по средней), равные
  средние (вторичный порядок), n = 0 в конце, «Пока нет оценок», курсор, отсутствие ПДн,
  сегменты не смешиваются, авторские оценки и оценки после превью учитываются.
