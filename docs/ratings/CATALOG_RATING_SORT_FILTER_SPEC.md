# Спецификация: сортировки и фильтры каталога по оценкам (проект, задача 612f9c76)

Статус: **ПРОЕКТ для решения Сергея. Ничего не включено.** Публичная выдача каталога,
расчёт рейтинга и права оценивания не меняются. Запуск только после отдельного OK.

## 1. Что есть сейчас

* Сортировки каталога: `new` (по умолчанию), `price_asc`, `price_desc`
  (`src/lib/catalog/listing-contract.ts`). Кандидаты сортируются в памяти
  (`listing.ts`), для не-`new` сортировок курсор позиционный. Добавить ключ сортировки
  можно без смены архитектуры.
* На PDP уже есть публичный агрегат `{ totalStars, ratingCount }` (без средней), берутся
  `excluded_at IS NULL`. В JSON-LD **нет** `AggregateRating`, и так и должно остаться, пока
  данные не очищены.
* Данные (скриншот 17.10, «всё время»): 379 пар, 39 аккаунтов, средняя 4,99, то есть почти
  все оценки — пятёрки. Сигналы IP/device ещё не объяснены (см. аудит). Масштаб: 1000+
  треков, около 300 продуктов.

## 2. Проблема, которую решаем

* **Средняя без учёта количества** ставит продукт с одной пятёркой выше продукта с сотнями
  оценок по 4,8.
* **Байес с глобальной средней не помогает при средней ≈5.** Если априорное `m` = 4,99, один
  голос 5★ даёт ≈4,99 и всё равно обгоняет 40 голосов по 4,9 (таблица ниже). Нужен
  **фиксированный нейтральный априор**.
* Сейчас голосов мало и они однородны. Любая «рейтинговая» выдача в основном показывает,
  кто активнее оценивал, а не что лучше.

## 3. Варианты

| Вариант | Формула | Плюсы | Минусы |
|---|---|---|---|
| A. «По средней оценке» | `sum/n` | понятно | 1 голос побеждает; при средней 4,99 сортировка почти случайна |
| B. «По количеству оценок» | `n` | устойчиво | награждает раскрутку, а не качество; уязвимо к массовым аккаунтам |
| **C. Байес с нейтральным априором (рекомендуется)** | `score = (C·m₀ + sum)/(C + n)`, `m₀ = 3,5`, `C = 10` | малое `n` прижимается к 3,5, большое `n` стремится к своей средней; одно число, легко объяснить | нужно подобрать `C`, `m₀` |
| D. Нижняя граница Уилсона | по доле «высоких» оценок (4–5★) | строго статистически | сложнее объяснить авторам; теряет разницу 4 vs 5 |
| E. «Популярные» | уникальные слушатели за 30 дней (eligible-пары или `playback_usage_facts`), **не оценки** | данных на порядки больше, оценки не нужны | не про качество; нужен тот же фильтр test/staff |

### Демонстрация (иллюстрация на типовых профилях; реальные цифры — запрос S5)

| Продукт | n | Средняя | Байес m=глоб. 4,99, C=10 | **Байес m₀=3,5, C=10** |
|---|---|---|---|---|
| A: 1 оценка, 5★ | 1 | 5,00 | 4,991 | **3,636** |
| D: 3 оценки, все 5★ | 3 | 5,00 | 4,992 | **3,846** |
| B: 40 оценок, средняя 4,90 | 40 | 4,90 | 4,918 | **4,620** |
| C: 200 оценок, средняя 4,70 | 200 | 4,70 | 4,714 | **4,643** |
| F: 12 оценок, средняя 4,25 | 12 | 4,25 | 4,586 | **3,909** |

С глобальным априором A и D (1–3 голоса) оказываются **наверху**. С нейтральным априором
наверху C и B (сотни и десятки голосов), A и D ниже F. Это ровно то поведение, которое
нужно: не продвигать продукты с одним голосом выше продуктов с десятками и сотнями оценок.

**На реальных данных:** запрос S5 в [`audit-2026-10-17-readonly.sql`](./audit-2026-10-17-readonly.sql)
печатает для каждого продукта (обезличенно, `P01…`) `n`, среднюю, рекомендуемый балл
`bayes_m0_35` (для сравнения и `bayes_global_c10`), места «по средней» и «по байесу» и
попадание в фильтр «Высоко оценённые». Ожидание при текущих данных: у всех средняя ≈5,0,
и места определяются почти только количеством. Это ещё один довод **не запускать** публичную
рейтинговую сортировку до очистки и роста данных.

## 4. Рекомендация

1. **Сортировка «Высоко оценённые»** = вариант C (`m₀ = 3,5`, `C = 10`; оба значения —
   настраиваемые константы в одном модуле, без «магии» в SQL).
2. **Фильтр «Высоко оценённые»**: `n ≥ N_min` (старт: 10) **и** `score ≥ 4,3`. Продукты с
   `n < N_min` в фильтр не попадают, но остаются в каталоге.
3. **«По количеству оценок»** в публичный UI **не выносить** (только админка). Публично
   отвечать на вопрос «что слушают» должна **«Популярные»** (вариант E), а не оценки.
4. **«По средней оценке» в чистом виде** публично не показывать.
5. **Что учитывать**: только `excluded_at IS NULL`. Тестовые аккаунты (`analytics_test_accounts`)
   и, по решению Сергея, оценки автора на свой продукт в балл не входят. Автоматически ничего
   не исключается.
6. **Порог запуска**: включать публичную сортировку, когда у ≥30 продуктов `n ≥ 10` от
   ≥100 разных аккаунтов **и** закрыт вопрос с IP-сигналом. До этого — только в админке.

## 5. Поведение без оценок (n = 0)

* Карточка: «Пока нет оценок». **Никогда** не «0,0» и не пустые звёзды, которые выглядят
  как плохая оценка.
* Сортировка «Высоко оценённые»: сначала все с `n ≥ 1` по `score`, затем без оценок по `new`.
  Без оценок балл не считается, и продукт не оказывается «посередине» искусственно.
* Фильтр «Высоко оценённые»: продукта нет в результате. Пустой результат — показать текст и
  ссылку на «Популярные».
* Новые продукты не наказываются: в `new` и «Популярных» оценки не участвуют.

## 6. Набросок реализации (после решения)

* Агрегат `practice_rating_aggregates(practice_id PK, rating_count, total_stars, updated_at)`
  с учётом фильтра test/owner. Обновление дельтами в `set_practice_rating` или периодическим
  пересчётом. Тяжёлых запросов в листинге нет: join по PK.
* `CATALOG_SORTS += "top_rated" | "popular"`. Ключ — балл из агрегата, тай-брейк
  `sortTimestamp`/`publication_id` (детерминированная пагинация).
* Публичный DTO: `ratingCount` и округлённая средняя (если `n ≥ N_min`). Никаких id и email
  оценивших.
* Флаг окружения (как appreciation-rollout), по умолчанию выключен.
* Тесты: порядок на фикстурах (A–F выше), `n = 0`, тай-брейки, курсор, отсутствие ПДн в DTO.
